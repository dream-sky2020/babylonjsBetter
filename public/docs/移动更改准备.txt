我不满意现在的移动系统，现在的移动系统有问题，现在的移动系统是，先让逻辑上的位置发生变动，然后视觉上播放移动动画，这导致会出现视觉和逻辑的错位
比如我要移动可操控角色到一个地方，看到敌人明明没有堵死路，但是逻辑上已经将路堵死，结果过不去了


所以我打算构建——实占位 + 虚占位 + 移动仲裁” 系统

1. 实体开始移动时，不立即改变实占位。 
   例如 NPC 从 A → B：
   - A 仍然是 NPC 的实占位，也就是实际位置依然在A。
   - B 创建一个 NPC 的虚占位（Reservation）。
   - 同时播放 A → B 的移动动画。

2. 虚占位存在一个提交时间 `Commit Time`
   在到达提交点之前，B 还不算真正被 NPC 占领。提交点最好与动画进度对应，例如移动到 50% 时提交：
   ```text
   A ────────●──────── B
             ↑
          Commit
   ```

3. 提交前，其他实体可以争抢虚占位。 
   每个移动请求拥有 `MovePriority`。如果另一个实体也要进入 B，由统一的 `MovementResolver` 比较优先级，这边优先级算法是（X*（已经移动的时间/走完一格需要的时间）+Y，X，Y都是可配置参数 ），而不是看谁的 Update 先运行。（默认玩家的优先级最高）

4. 如果虚占位被抢走，则 Rollback
   NPC：
   ```text
   删除 B 的虚占位
   → 实占位仍然保持 A
   → 当前移动失败
   → 从当前视觉位置播放退回 A 的动画（就像是角色移动失败的动画一样，不要改变角色的朝向!）
   ```
   所以逻辑不会为了等待动画而卡住。

5. 如果到达 Commit Point 仍未被抢占，则正式提交。
   ```text
   释放 A 实占位
   B 虚占位 → B 实占位
   ```
   此后 B 不再允许其他普通移动请求抢占。

整个移动过程因此可以抽象成：

```text
Request Move
     ↓
检查目标
     ↓
Reserve（虚占位）
     ↓
播放移动动画
     ↓
   仲裁阶段
   ↙     ↘
被抢占    到提交点
  ↓         ↓
Rollback   Commit
  ↓         ↓
返回原位   正式占领目标格
```

核心数据可以分成三块：

```cpp
Occupancy       // 当前真正占据哪一格
Reservation     // 正在尝试进入哪一格
MoveRequest     // 移动请求、优先级等
```

然后由一个统一的：

```cpp
MovementResolver
```

负责处理**多人抢格、优先级、提交和回滚**。

这样以后玩家/NPC抢路、两人换位、冲锋、击退、推挤、大型敌人移动等，都可以继续建立在同一套机制上，而不用各写一套特殊逻辑。

一句话概括就是：

移动不再是“先修改逻辑位置，再播放动画”，而是“先预留目标位置 → 动画移动 → 期间允许仲裁 → 到达临界点后正式提交占位”。
